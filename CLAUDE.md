# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

BusBee user-side app: a Flutter client (`flutter_app/`) for searching buses and tracking them live, backed by a Node/Express 5 + PostgreSQL (PostGIS) API with a WebSocket server (`backend/`). The project was migrated off Firebase/Firestore; nothing Firebase-related remains (don't reintroduce the `google-services` Gradle plugin). A separate driver app (not in this repo) is expected to push locations over the WebSocket.

## Commands

### Backend (`backend/`)
```sh
npm install
cp .env.example .env      # set DB_* and JWT_SECRET (PORT defaults to 5000)
npm run dev               # nodemon src/server.js
npm start                 # node src/server.js
npm test                  # node test_ws.js — boots the server in-process and runs WebSocket integration checks
psql -d busbee_db -f db/schema.sql   # create tables (idempotent; needs PostGIS)
psql -d busbee_db -f db/seed.sql     # optional sample buses/routes around Kochi (seeded bus KL-07-101 = 11111111-1111-1111-1111-111111111101)
npm run db:check          # compare the .env database with db/schema.sql (read-only; exit 1 on differences)
npm run db:reset          # drop schema.sql's tables and recreate them (local DB_HOST only; add -- --seed, -- --force if tables have rows)
npm run simulate          # fake driver: moves a seeded bus along its route_coordinates over the WebSocket (-- <bus-uuid> for another bus)
```
`GET /api/health` also reports `database: connected|disconnected`.
`npm test` starts the real server on `PORT`, so stop any running dev server first. It never uses a database: it points `DB_HOST`/`DB_PORT` at a closed port, so bus existence checks and location persistence always fail and are tolerated. It signs its own driver tokens (`JWT_SECRET` falls back to `test-secret`) and waits for async replies such as `driver_registered` with `waitFor`. `test_ws.js` covers the whole WebSocket protocol (driver auth, aliases, query-string subscriptions, errors); extend it when you change `websocket.js`. There is no linter or unit-test framework for the backend, and no migration tool: `db/schema.sql` is the source of truth for the schema. When you add a column, add it to the `CREATE TABLE` and also as an `ALTER TABLE … ADD COLUMN IF NOT EXISTS` so re-running the file upgrades existing databases.

flutter pub get

### Testing on a physical Android phone (local backend)
The dev machine is Windows (PowerShell). `psql` and `adb` are not on PATH: use `& "C:\Program Files\PostgreSQL\18\bin\psql.exe"` and `& "$env:LOCALAPPDATA\Android\Sdk\platform-tools\adb.exe"`, or prefer `npm run db:reset -- --seed`, which needs no `psql`. The local database is whatever `DB_NAME` in `backend/.env` says (not necessarily `busbee_db`). Workflow, one terminal each:
```powershell
# backend/
npm run dev
# flutter_app/ (phone connected over USB with USB debugging on; re-run adb reverse after every replug)
& "$env:LOCALAPPDATA\Android\Sdk\platform-tools\adb.exe" reverse tcp:5000 tcp:5000
flutter run --dart-define=API_BASE_URL=http://localhost:5000 --dart-define=WS_BASE_URL=ws://localhost:5000
# backend/
npm run simulate          # moves seeded bus KL-07-101 so the timeline shows a live bus
```
`http://localhost:5000/api/health` in the phone's browser checks the phone → server → database chain. Plain `http`/`ws` works on the phone only because `android/app/src/debug/AndroidManifest.xml` sets `usesCleartextTraffic="true"`. That applies to debug builds only, so release builds need `https`/`wss`. Over Wi-Fi instead of USB, use the PC's LAN IP and allow inbound TCP 5000 in Windows Firewall. The seeded `bus_locations` row goes stale for `/nearby` after 10 minutes unless the simulator is running. Only KL-07-101 has `route_coordinates`. The dev scripts (`simulate_driver.js`, `check_schema.js`, `reset_db.js`) live in `backend/scripts/`.

## Architecture

### Backend
- `src/server.js` creates an `http.Server` wrapping the Express app and attaches the WebSocket server (`src/websocket.js`) to the **same port**. It exports `app` with `app.server`/`app.wss` attached (used by `test_ws.js` to shut down).
- REST routes: `GET /api/health`, `/api/auth` (`POST signup`, `POST login`, `GET /me` behind the `protect` JWT middleware in `src/middleware/auth.js`) and `/api/buses` (`search?number=`, `trips?from=&to=`, `nearby?lat=&lng=&radius=` (metres, default 2000), `:id/route`). In `busRoutes.js`, `/:id/route` must stay last; it returns 400 `Invalid bus id.` for non-uuid ids. Bus routes and WebSocket subscriptions are unauthenticated; only WebSocket driver registration needs a token. `helmet` is applied globally and `/api/auth` is rate limited to 20 requests per IP per 15 minutes (`express-rate-limit`; set `trust proxy` if deployed behind a proxy). The server exits at startup when `JWT_SECRET` is missing.
- Responses are JSON. Errors are always `{ message }`; unknown routes return 404 `{ message: 'Route not found.' }` (the Flutter `BusService` prefix fallback keys on this text). Success shapes: auth → `{ token, user }` / `{ user }`; search → `{ bus }`; trips/nearby → `{ buses }`; route → `{ route }`.
- Auth: bcrypt hashes, JWT signed with `JWT_SECRET`, 7-day expiry, payload `{ id, name, email, role }`. Emails are lower-cased. `signup` always creates `role = 'user'` and ignores any `role` in the body; drivers and admins are promoted in SQL (`UPDATE users SET role = 'driver' WHERE email = …`). There is no refresh-token endpoint.
- `src/db.js` exposes a `pg` Pool (idle-client errors are logged, not fatal) and a `query(text, params)` helper; always use parameterised queries. The schema is in `db/schema.sql`: `users`, `buses` (uuid `id`; `stops` is a JSONB array of stop-name strings), `bus_locations` (one row per bus: `geom` point SRID 4326, `heading`, `speed`, `updated_at`), `route_coordinates` (`bus_id`, `seq`, `name`, `geom`). Bus ids are uuids. PostGIS points are (lng, lat): `ST_MakePoint(lng, lat)`, `ST_X` = lng, `ST_Y` = lat.
- `searchTrips` matches buses where `from` comes before `to` in the ordered sequence `start_location → stops[] → end_location` (case-insensitive exact names). `nearby` only returns buses whose `bus_locations` row was updated in the last 10 minutes (`LOCATION_FRESHNESS` in `busController.js`).
- **WebSocket protocol** (`src/websocket.js`): live state is held **in memory**, so it only works on a single server instance. Every connection first gets `{ type: 'connected' }`. Drivers log in through `/api/auth/login` and send `register_driver` with `busId` and `token` (or connect with `?role=driver&busId=…&token=…`). The token must be a valid JWT with `role: 'driver'` and the bus id must be a uuid that exists in `buses` (if the database is unreachable the existence check is skipped with a warning). Registration is async, so drivers should wait for `driver_registered` before sending `location_update` (`lat`/`latitude`, `lng`/`longitude`, `heading`, `speed`; `busId` is optional), which is acknowledged with `location_ack`. Location updates are rejected from unregistered connections and for any bus other than the one the connection registered for. The server caches the latest location per bus, broadcasts it to subscribers, and upserts it into `bus_locations` in the background (failures are logged once per distinct error and otherwise ignored). Users send `subscribe` / `unsubscribe` / `subscribe_all` / `get_location` / `ping` and receive `subscribed`, `unsubscribed`, `not_found`, `pong`, or `error`. They can also subscribe through the connection query string (`?role=user&busId=…`, `?subscribe=*`). New subscribers get the cached location immediately. Outgoing `location_update` payloads repeat each field under both naming styles (`busId`+`bus_id`, `lat`+`latitude`, `lng`+`longitude`), so clients can read either. Message types are accepted under several aliases (`msg.type || msg.action || msg.event`), dispatched through the `messageHandlers` map to one `handle*` function per type; build outgoing location messages with `locationPayload()`. A 30 s ping/pong heartbeat terminates dead sockets.

### Flutter client
- `lib/main.dart` calls `determineInitialScreen()`, which validates the stored JWT through `AuthService.getCurrentUser()` (`/api/auth/me`). It routes to `BusSearchScreen`, or to `LoginScreen` when there is no token or the token is invalid (it clears the token on 401/403/404). Navigation uses plain `Navigator.push` with `MaterialPageRoute`; Settings logs out with `pushAndRemoveUntil` back to `LoginScreen`. There is no router package and no state-management library (`setState` only).
- **Visual style** (modelled on a dark gradient hero design, Dribbble "Dark Gradient Hero Section #2"): a fixed dark theme from `lib/theme/app_theme.dart` (`AppTheme.dark()`), with pitch-black pages, hairline borders (`AppColors.border`, `AppTheme.hairline`), large light headings that fade grey → white, silver gradient buttons (the `ElevatedButton` theme draws `AppTheme.silverGradient` through `backgroundBuilder`) and soft ember-orange glows (`AppColors.emberDeep` → `emberMid` → `peach` → `glow`, accent `AppColors.ember`, horizon halo `AppColors.horizon`). The colour values were sampled from the shot itself, so keep them when restyling. `main()` sets light status/navigation-bar icons. Use `AppColors`/`AppText` instead of raw colours or `TextStyle`s. All text uses the bundled **Manrope** (`AppFonts.body`), a static TTF set in `assets/fonts/` (OFL licence alongside), declared in `pubspec.yaml`, and not fetched at runtime, so don't add `google_fonts`. Shared building blocks are in `lib/widgets/brand.dart` (`BrandWordmark`, `GlowBackdrop` with `GlowStyle.top/horizon/sweep/bottom`, `NavBarPill`, `NavBarButton`, `AnnouncementPill`, `GradientHeadline`, `RoundIconButton`, `Pill`, `GlassPanel`, `SectionHeader`, `InlineMessage`, `LiveDot`) and `lib/widgets/auth_scaffold.dart` (the shared login/sign-up layout, plus `ButtonSpinner`). Glows and the live dot are deliberately static: screen tests use `pumpAndSettle`, so never-ending animations on these screens would hang them. `GlowStyle.horizon` is not clipped to its box (it fades into the content below); the other styles are.
- Screens (`lib/screens/`): `LoginScreen` ↔ `SignUpScreen` → `BusSearchScreen` (search by bus number, by from/to trip, and "nearby" via `LocationService`) → `BusRouteDetailsScreen` (a "Where is my Train"-style vertical stop timeline with the live bus from the WebSocket stream, a status card ("Live · updated Xs ago", "Between A and B" / "At X", off-route and stale warnings), and a "Go to Google Maps" button that opens the route through `url_launcher`; there is no embedded map). `SettingsScreen` holds logout.
- Screens hold UI and state only; logic lives in services and reusable widgets live in `lib/widgets/` (`BusCard`, `RouteTimelineTile`). `services/route_progress.dart` (`RouteProgressTracker`) is pure logic: it snaps a bus position onto the line through the resolved stops and returns `RouteProgress` (`fromIndex`/`toIndex`, `fraction` 0–1, `atStopIndex` within 100 m, `offRouteMetres`), ignoring backwards moves under 50 m (GPS jitter). `RouteTimelineTile` must be laid out at its fixed `height` (`ListView(itemExtent: RouteTimelineTile.height)`), because each tile draws the connector to the next stop and places the bus icon at `fraction` of that height. Timeline rows are the resolved route stops, so `route_coordinates` rows should be stops (each row becomes a timeline stop); without at least 2 resolved stops the timeline shows `routeStopNames` without a bus. `services/location_service.dart` (`LocationService`) wraps permissions, GPS and reverse geocoding and throws `LocationException` with a user-facing message. `services/route_resolver.dart` (`RouteResolver`) turns a `BusInfo` into map points: it uses `/api/buses/:id/route` when that returns at least 2 points, otherwise it geocodes `BusInfo.routeStopNames`, adding hints such as "Kochi, Kerala, India" (capped at 8 stops off-web). `utils/google_maps_links.dart` builds the "Open in Google Maps" URL.
- `BusRouteDetailsScreen` subscribes with `bus.id ?? bus.number`, listens to the stream in `initState` and cancels it in `dispose` (which sends `unsubscribe`).
- `services/api_client.dart`: `ApiClient` wraps `package:http` (15 s timeout), adds the bearer token when a call passes `requiresAuth: true` (through an injected `tokenProvider`), and turns every failure (HTTP ≥ 400, timeouts, network, bad JSON) into `ApiException(message, statusCode, data)`, taking `message` from the server's `message`/`error` field. The default base URL comes from `--dart-define=API_BASE_URL`, falling back to `http://10.0.2.2:5000` on the Android emulator and `http://localhost:5000` elsewhere.
- `services/auth_service.dart`: stores tokens in `flutter_secure_storage` (`auth_access_token`, plus `auth_refresh_token` if the server ever returns one) and re-exports `api_client.dart` and the models, so screens usually import only `auth_service.dart`.
- `services/bus_service.dart`: REST calls under `/api/buses` (on a route-not-found 404 it retries with `/api/v1/buses` and keeps whichever prefix worked). `searchBusByNumber` returns `null` on 404. `subscribeBusLocation()` opens a `WebSocketChannel`, sends `subscribe`, emits `location_update` maps, and sends `unsubscribe` on cancel. When the socket drops it reconnects and resubscribes with exponential backoff (1 s doubling to 30 s, reset on any message) until cancelled. Tests inject a `connect` factory to exercise this; an injected `channel` without `connect` is used once and the stream closes when it ends. The WS URL comes from `WS_BASE_URL` or is derived from the HTTP base URL (`http`→`ws`, `https`→`wss`).
- Models (`lib/models/`): `BusInfo.fromJson` accepts both snake_case backend keys and camelCase/legacy Firestore keys (`bus_number`/`busNumber`/`number`, `distance_km`/`distanceKm`, `start_location`/`start`, …). Keep that tolerance when you change payloads. `UserModel` and `AuthResponse` are plain classes with hand-written `fromJson`/`toJson` (no codegen).
- **Testability through constructor injection:** screens take optional `authService`/`busService`/`locationService` parameters (and `BusRouteDetailsScreen` takes a `routeResolver` and `wsChannel`) and create defaults once (in `initState` or a `late final` field, never in a getter), services take `ApiClient`/`FlutterSecureStorage`, `ApiClient` takes an `http.Client`, and `subscribeBusLocation` takes a `channel`. Tests use `MockClient` from `package:http/testing.dart` plus the fakes in `test/test_helpers.dart` (`FakeSecureStorage`, `FakeLocationService`, `FakeWebSocketChannel`, which exposes `incoming`/`outgoing` stream controllers, and `tapVisible(tester, finder)`, which scrolls a widget into view before tapping; use it, because pages are taller than the 800×600 test surface); `RouteResolver` takes a `geocode` function. Keep new services and screens injectable the same way.
- `google_maps_flutter` is still a dependency for its `LatLng` type (used by `RouteResolver`, `RouteProgressTracker` and the Google Maps link builder); no screen renders a `GoogleMap` any more. The Maps API keys are configured in `web/index.html` and `android/app/src/main/AndroidManifest.xml`. Don't use the deprecated `dart:js`.
- Errors are not swallowed silently: Flutter code logs caught exceptions with `debugPrint` (prefixed by area, e.g. `[BusSearch]`) before showing a user-facing message or falling back; the backend logs with `console.error`/`console.warn`. Keep new `catch` blocks consistent with this.
